# 性能基准

> 记录日期：2026-10-30 ｜ 框架版本：v0.42.0

---

## 怎么看这份数据

**只看相对关系，不看绝对值。**

同一台机器上的「1000 次循环 vs 批量」能回答「insertMany 快多少倍」，
这个结论换台机器依然成立。但「141 ms」换台机器就没意义了——
CPU、磁盘、PHP 版本、Docker 网络都会改变它。

所以本文档的结论都写成「快 N 倍」「慢 N 倍」，**不写成「耗时 X ms」**。

---

## 如何复现

```bash
# SQLite 内存库（默认，无需配置）
php scripts/benchmark.php

# MySQL
SR_TEST_DB=mysql SR_TEST_DB_NAME=sr_test \
SR_TEST_DB_USER=root SR_TEST_DB_PASS=root \
php scripts/benchmark.php

# PostgreSQL
SR_TEST_DB=pgsql SR_TEST_DB_NAME=sr_test \
SR_TEST_DB_USER=postgres \
php scripts/benchmark.php
```

脚本直接输出 markdown，可以贴进任何文档。

**方法**：

- 每项跑 3–5 轮取**中位数**（GC、CPU 调频会让单次结果抖动几倍）
- 每轮开始前**预热一次**（首次连库、文件创建、类加载不计入）
- 计时用 `hrtime(true)`（纳秒精度，单调时钟）

## 数据库

### 插入 1000 条：循环 vs 批量

| 数据库 | 循环 `insert()` | `insertMany()` | 提速 |
| --- | --- | --- | --- |
| SQLite（内存） | 3.6 ms | 0.9 ms | **3.9×**（复跑 4.0×，稳定） |
| MySQL 8.0 | 141 ms | 4.5 ms | **31–40×**（复跑 178ms / 4.4ms，波动大） |
| PostgreSQL 18 | 116 ms | 3.1 ms | **36.9×** |

> **注意这里的波动**：MySQL 的循环插入两次测出 141ms 和 178ms（差 26%），
> 提速从 31.5× 变成 40.3×。原因是每次 `insert` 都触发一次 WAL fsync，
> 受磁盘缓存命中率影响很大。
>
> 所以**连相对值也有 ±30% 的波动**。结论只能说到「快一个数量级以上」，
> 不能说到「快 31.5 倍」。SQLite 内存库反而稳定（3.9× vs 4.0×），因为它不碰磁盘。

**这是本文档最有实际价值的一组数字**。

SQLite 内存库只快 3.9×，因为根本没有网络往返——它和 PHP 在同一个进程里。
真实数据库上，循环插入的瓶颈是**每次一次往返**（约 1.4ms），
批量插入把 1000 次往返压成 1 次。

所以：

- 在 SQLite 上测出的批量插入收益**严重低估**
- 生产环境用 MySQL / PostgreSQL 时，批量插入是**数量级**的差异，不是百分比
- 这也是为什么「给 1000 个用户发通知」必须用 `insertMany`

### 查询

| 数据库 | 查询 1000 行 | `COUNT(*)` × 10 | `GROUP BY` × 5 |
| --- | --- | --- | --- |
| SQLite（内存） | 0.2 ms | < 0.1 ms | 0.9 ms |
| MySQL 8.0 | 0.4 ms | 1.6 ms | 3.7 ms |
| PostgreSQL 18 | 0.3 ms | 1.3 ms | 2.1 ms |

三个库在**简单查询**上差距很小（都是毫秒级），差异主要体现在批量写入。

PostgreSQL 的 `GROUP BY` 比 MySQL 略快（2.1ms vs 3.7ms），但样本太小，
不足以作为选型依据。

## 缓存

1000 次 `put` + `get`，3 轮取中位：

| 驱动 | 中位耗时 | 相对 array |
| --- | --- | --- |
| `array` | 0.4–0.6 ms | 1× |
| `redis` | 109–111 ms | **约 200–270×** |
| `file` | 172–174 ms | **约 300–430×** |

**两个反直觉的结论**：

1. **`file` 比 `redis` 还慢**。文件驱动每次 `put` 都要 `fopen` + `fwrite` + `rename`（原子写），
   而 Redis 只是一次 TCP 往返。在本机回环上，TCP 比文件系统调用更快。

2. **`array` 与网络驱动差两个数量级**。这不代表 Redis 慢——10000 次操作 109ms
   意味着**每次 11 微秒**，对网络存储来说完全正常。
   差别在于 `array` 是纯 PHP 数组操作，没有序列化和 I/O。

**实践含义**：单次缓存操作的开销（约 10 微秒）相对于一次数据库查询（约 1000 微秒）
可以忽略，所以「缓存该不该用」的判断依据是**能否减少数据库查询**，
而不是缓存本身的读写速度。

## 图片

1600×1200 JPEG → 300×300 WebP（quality 80），5 轮取中位：

| 驱动 | 中位耗时 | 输出体积 |
| --- | --- | --- |
| `gd` | 14.3 ms | 6.4 KB |
| `imagick` | 33–35 ms | 6.6–7.5 KB |

**GD 快 2.3×，体积还略小。**

这与「Imagick 质量更好」的常见认知不矛盾——Imagick 用的是 Lanczos 重采样，
理论上画质更优；但在 **300×300 这个尺寸上，肉眼几乎看不出差异**，
而代价是 2.3 倍的时间（Imagick 还有进程外编解码的开销）。

所以框架的 `auto` 默认选 GD（见 v0.35.1），需要精修大图时显式配 `imagick`。

> 这个结论有测试守着：`ImageTest::testAutoPrefersGd`。
> 有人把优先级改回 Imagick 会立刻红，失败信息里写了原因。

## 队列

| 操作 | 中位耗时 |
| --- | --- |
| 入队 1000 条 | 4.6 ms |
| 单条入队 | 约 0.05 ms |

单条入队约 50 微秒（含 JSON 序列化 + 一次 INSERT），
这意味着**「异步化」本身的成本可以忽略**——
把邮件通知放进队列，相比 SMTP 的 1–3 秒，入队耗时不到千分之一。

## 结论汇总

| 结论 | 数据支撑 | 影响的设计决策 |
| --- | --- | --- |
| 批量插入在真实数据库上是**数量级**差异 | MySQL 31–40× / PG 37×；SQLite 仅 4× | 通知必须用 `insertMany`（v0.31） |
| 缓存操作比数据库查询快两个数量级 | 11 μs vs 1000 μs | 缓存用来减少查询，不是加速单次访问 |
| `file` 缓存比 `redis` 慢 | 172ms vs 109ms | 多机部署必须用 Redis |
| GD 比 Imagick 快 2 倍以上，缩略图质量无差异 | 14ms vs 34ms | `auto` 默认 GD（v0.35.1） |
| 入队成本可忽略 | 50 μs vs SMTP 的 1–3 s | 邮件通知一律异步（v0.32） |

## 已知局限

| 局限 | 说明 |
| --- | --- |
| 只在本机测 | 跨网络、跨可用区的延迟差异未覆盖 |
| **相对值也有 ±30% 波动** | MySQL 两次测出 31.5× 与 40.3×；结论只能说到「数量级」 |
| 数据量小 | 1000 条；10 万条时的索引行为未测 |
| 无并发 | 单进程串行；并发下的锁竞争未覆盖 |
| 无长时间运行 | 未观察 GC、内存增长趋势 |

这些需要专门的压测环境（固定规格 runner + 压测工具），
属于 v1.1 的范围。**当前的目的是为架构决策提供依据，不是给 SLA 背书。**
